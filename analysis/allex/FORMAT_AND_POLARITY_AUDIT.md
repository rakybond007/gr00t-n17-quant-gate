# allex 프롬프트 포맷 점검과 부호 검증 (2026-09-13)

정답지는 사용자가 준 naive 균등 배속 eval 이다 (`naive_speedup_eval.json`,
칸마다 30 에피). 1x 기준선은 아직 없어서 **유지율이 아니라 성공 수**다.

## 포맷: 맞다. 한 곳만 빠져 있었다

| 항목 | 상태 |
|---|---|
| 계산값 넘기는 형식 | robocasa `facts_text` 와 같다 -- 임계 판정을 코드가 끝내고 결론 문장만 준다 |
| 줄 수 | 조건과 무관하게 항상 여섯 줄 (배치 패딩을 피하려고 고정) |
| 지시문 | 앞에 붙는다 (robocasa phase9 와 같다) |
| 등급 경로 | `judge_batch(n_grade=5)` -> 서버가 배치를 언제나 `judge_text_batch` 로 보낸다. 모델이 글로 답하고 서버가 읽는 경로다 |
| 등급 기댓값 | `eg` 가 100% 행에 실려 있다. robocasa·libero 가 고치기 전부터 여기선 돌고 있었다 |
| **원본 등급 분포 `gp`** | **빠져 있었다** -- 이번에 추가 |
| 실행 설정 기록 | 빠져 있었다 -- `records_meta.json` 추가 |

`gp` 가 없으면 가중은 다시 잡을 수 있어도(eg 가 있으니) **분포 모양을 못 본다.**
P(3)=0.9 와 P(2)/P(3)/P(4)=.3/.35/.3 은 eg 가 거의 같은데 전혀 다른 상태다.

### 임계값은 잘 맞춰져 있다

robocasa 는 속도 임계 0.12/0.50 이 실제 분포의 1.6/46.6 분위에 있어서 한 칸이
비었다(101점 분위표로 고쳤다). allex 는 그 문제가 없다 -- 표본 11,460행 기준:

| 특징 | 임계 분위 | 세 칸 비율 |
|---|---|---|
| gap_mean | 42.7% / 76.0% | 42.7 / 33.3 / 24.0 |
| arm_speed | 29.9% / 66.6% | 29.9 / 36.7 / 33.4 |
| hand_change | 35.7% / 55.0% | 35.7 / 19.3 / 45.0 |
| wrist_rot | 43.1% / 65.1% | 43.1 / 21.9 / 34.9 |

빈 칸이 없다. 이 층은 손댈 것이 없다.

## 부호: 뒤집혀 있다

칸 여섯을 다 덮는 실행은 `allex_loop_158163` 하나뿐이다. **이 실행의 표본이
`output/allex_sample/D.json` 이고, 6층 x 125 = 750 청크로 층별 검정력이 같게
뽑힌 집합이다**(`allex_v3_sample.py`). 우연히 균형이 맞은 게 아니라 그렇게
설계된 표본이라 칸별 conf 추정의 정밀도가 같다.

집계 단위를 바꿔도 결과가 그대로다.

| 집계 단위 | 단위 수 | 2.0x | 2.5x |
|---|---|---|---|
| 청크마다 | 750 | -0.754 (p=0.084) | -0.886 (p=0.019) |
| 에피소드(ep)마다 | 80 | -0.812 (p=0.050) | -0.829 (p=0.042) |
| (ep, task) 마다 | 277 | **-0.899** (p=0.015) | **-0.943** (p=0.005) |

셋 다 강하게 음수다 -- 집계 방식을 고르다 나온 값이 아니다.

```
conf 낮은->높은:  Pass·box < Pass·bag < Bring·box < Bring·bag < Rotate·bag < Rotate·box
성공 낮은->높은:  Rotate·box < Bring·bag < Rotate·bag < Bring·box < Pass·bag < Pass·box
```

**순서가 거의 정확히 거꾸로다.** conf 가 가장 압축하기 어렵다고 한 Pass 는 두
배속에서 한 번도 안 떨어진다(30/30, 29/30). 가장 안전하다고 한 Rotate Box 가
2.5x 에서 16/30 으로 가장 깨진다.

### 문항 하나를 빼서 고쳐지지 않는다

(ep, task) 집계 · 2.5x 기준:

| 뺀 문항 | 상관 |
|---|---|
| (전부 다섯) | -0.943 |
| CLAMP | -0.771 |
| LOOSE | -0.771 |
| **SHOVE** | **+0.200** |
| FLIP | -0.886 |
| FREE | -0.886 |

SHOVE 제거만 부호를 뒤집는데 **이건 집계에 민감하다** -- 에피소드 집계에서는
SHOVE 를 빼도 -0.371 로 음수다. 그래서 "SHOVE 하나가 범인" 이라고 말할 수 없다.
말할 수 있는 것은 SHOVE 가 가장 크게 틀린 방향으로 기여한다는 것이다. 문항
둘까지 빼도 최선이 +0.257 (p=0.62) 이다.

robocasa v1 이 -0.705 였고 문항 A 재조준 하나로 +0.502 가 된 것과 같은 자리인데,
거기서는 범인이 한 문항으로 깔끔히 갈렸고 여기서는 안 갈린다.

### 이것을 최종 결론으로 쓰면 안 되는 이유

* **칸이 여섯이고 넷이 천장에 붙어 있다.** Pass 둘은 두 배속 모두 만점급,
  Bring Box 와 Rotate PolyBag 은 27/26. 실제로 갈리는 것은 Rotate Box 와
  Bring PolyBag 둘뿐이고, p 값은 6점 위의 값이다.
* **ablation p 값은 의미가 거의 없다** -- 조합을 여럿 훑었다.
* **그 실행의 가이던스를 되찾을 수 없다.** allex 가이던스는 `allex_v3_checks.py`
  에 박혀 있고 그 파일은 그 뒤로 판올림됐다(실행 09-05 18:01, 파일 09-05 22:20).
  `run_scripts/label/` 에 09-05 01:45 사본이 있지만 문항 이름이 A~E 인 앞
  세대다. 그래서 위 숫자는 **그때의 프롬프트**에 대한 것이고, 지금 것과 같다는
  보장이 없다.
* 1x 기준선이 없어 유지율이 아니라 성공 수다.

### 그래서 무엇을 돌렸나

지금 프롬프트로 **D 를 다시 재고, 한 번도 안 쓴 `H.json`(역시 6층 x 125 = 750)
으로 확인한다.** D 에서 나온 부호를 D 로 다시 확인하는 것은 확인이 아니므로
홀드아웃이 핵심이다. 잡 180772, libero 전량 라벨링(180685) 뒤에 시작하도록 걸어
두었다 -- GPU 를 두고 경쟁하지 않는다.

재현: `python scripts/allex_polarity.py output/allex_D_current/records.jsonl`

## 이미 알던 것과 맞물린다

감점 문항 둘이 등급 상단에서 죽어 있다 -- CLAMP 는 10개 실행 전부에서 4등급
이상이 **0.0%**, LOOSE 는 평균 0.5%. 위험 변이 작동하지 않으면 conf 는 가점
변(SHOVE/FLIP/FREE)이 정하고, 그 셋이 Rotate Box 에서 높다(SHOVE 4.26). 상자를
돌리는 것을 "한 번 밀면 알아서 가는 일" 로 읽은 것인데, 그 칸이 가장 많이 깨진다.

## 정답지는 맞았고, 라벨은 게이트를 통과하지 못한 판으로 만들어졌다

"정답만 비슷하게 나오게 깎아놓고 라벨링은 이전 버전으로 했나" 를 확인한 결과는
**반대**다.

### 정답지(운용자 상한표)는 정확하다

부호 게이트는 `TASK_RANGE` -- 운용자가 준 칸별 허용 배속 띠 -- 의 가운데값으로
위험/안정을 가른다. 그 순서가 실측과 거의 그대로다.

| 칸 | 상한 띠 | 가운데 | 실측 2.5x | 유지율(1x=30/30 가정) |
|---|---|---|---|---|
| Rotate Box | 1.5~2.0 | 1.75 | 16/30 | 0.533 |
| Bring PolyBag | 1.5~2.5 | 2.00 | 23/30 | 0.767 |
| Rotate PolyBag | 2.0~2.5 | 2.25 | 26/30 | 0.867 |
| Bring Box | 2.0~3.0 | 2.50 | 27/30 | 0.900 |
| Pass PolyBag | 2.0~3.0 | 2.50 | 29/30 | 0.967 |
| Pass Box | 2.0~3.0 | 2.50 | 30/30 | 1.000 |

위험 셋 {Rotate Box, Bring PolyBag, Rotate PolyBag} 이 실측 하위 셋과 **동일**하다.
그리고 v2 를 맞추는 항목 [7] 은 합격선에서 **일부러 뺐다** -- 코드에 이유가 적혀
있다: "v2 는 정답지가 아니라 다른 프롬프트로 뽑은 같은 모델의 출력이다. 거기
맞추라고 게이트를 걸면 v3 의 목표가 v2 의 재현이 된다."

즉 정답지에 맞춰 깎은 것이 아니다.

### 그 라벨을 만든 판은 자기 게이트에서 떨어진 판이다

`allex_v3_verify.py` 를 158163 라벨에 그대로 돌리면:

```
[3] 부호가 맞는가
      CLAMP  감점  위험 2.75  안정 2.69  차 +0.06   맞음
      LOOSE  감점  위험 1.61  안정 1.35  차 +0.26   맞음
      SHOVE  가점  위험 3.57  안정 2.36  차 +1.21   틀림   <-
      FLIP   가점  위험 1.89  안정 1.54  차 +0.34   틀림   <-
      FREE   가점  위험 3.34  안정 3.46  차 -0.12   맞음
[4] 문항 상관   LOOSE-FLIP +0.724   미달
=== 판정 ===  3 부호 2.000 (기준 0) 미달 · 전체: 미달
```

`verify.json` 에도 그대로 남아 있다(형식만 통과, 상관·칸구분 미달). **탐색
중이던 판이고 채택된 판이 아니다.** 그래서 "정답에 맞춰 깎은 뒤 옛 판으로
라벨링했다" 가 아니라, **부호 검사가 떨어진 상태로 라벨이 나갔다**.

### 그래서 앞서 한 말 하나를 정정한다

"한 문항이 잘못 조준된 게 아니라 집합 전체가 반대" 라고 했는데, **문항 수준에서는
깔끔히 갈린다.** 범인은 SHOVE(+1.21, 압도적으로 큼)와 FLIP(+0.34)이고 CLAMP·LOOSE·
FREE 는 방향이 맞다. conf 수준의 leave-one-out 이 흐릿했던 것은 conf 가 변마다
가중평균을 하기 때문이다 -- 문항 둘을 같이 빼면 +0.257 로 부호가 돌아온다.

SHOVE = "한 번 밀면 알아서 가는 일인가" 가 Rotate 에서 3.57 로 뜬다. 상자를
돌리는 것을 밀어 보내는 동작으로 읽은 것인데, 그 칸이 가장 많이 깨진다.
FLIP = "아무 데나 잡아도 되는 것인가" 는 LOOSE 와 0.724 로 겹쳐 있어 중복이기도 하다.

### 등급 눈금이 눌려 있다

```
CLAMP 쓴 등급 [1,2,3]      <- 4·5 를 한 번도 안 씀
FREE  쓴 등급 [3,4,5]      <- 1·2 를 한 번도 안 씀
```

감점 문항이 상단을 못 쓰고 가점 문항이 하단을 못 쓴다. 두 변이 다 좁은 구간에서만
움직이므로 conf 가 벌어질 여지가 작다(실측 표준편차 0.058).
