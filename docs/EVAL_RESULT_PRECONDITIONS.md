# 문항 설계에 앞서 갖춰야 할 것

문항(checks)을 근거 있게 깎으려면 **문항을 채점할 바깥 기준**이 있어야 한다. 이 문서는
그 기준이 어떤 형태로 있어야 하는지, 어디에 있는지, 없으면 무엇을 못 하는지를 적는다.
여기 있는 것이 다 갖춰져 있으면 `QUESTION_DESIGN_HARNESS.md` 의 절차가 그대로 돈다.

---

## 1. 폐루프 평가 결과 (필수)

문항이 **태스크 수준에서 옳은 방향인지**를 재는 유일한 근거다. 이것 없이 문항을 고치면
방향이 거꾸로인 채로 고도화된다 -- 실제로 그런 일이 있었다(아래 8절).

### 있어야 할 것

같은 정책·같은 시드로 돌린 **압축 없음 1회 + 압축 K배 1회 이상**.

```
output/robocasa/<런이름>/<태스크이름>/prediction.txt
```

`prediction.txt` 는 에피소드당 한 줄:

```
episode 0 is_success: [False] action_steps: 1000
episode 1 is_success: [ True] action_steps: 161
```

파싱은 `is_success:\s*\[\s*(True|False)\s*\]` 로 한다. **줄 끝에 덧붙인 요약 헤더를
쓰면 안 된다** -- 헤더로 성공률을 계산했다가 K4 가 K3 보다 좋다는 불가능한 결과를 얻은
적이 있다. 반드시 에피소드 줄을 센다.

### 우리 쪽 실제 경로

| 런 | 내용 | 태스크 | 에피/태스크 |
|---|---|---|---|
| `baseline_full_v2_with_action_steps` | 압축 없음 | 24 | 50 |
| `baseline_compress_K2` | 전 구간 K=2 | 24 | 50 |
| `baseline_compress_K3` | 전 구간 K=3 | 24 | 50 |

### 여기서 만드는 값

```
유지율(task) = 성공률(압축 K) / 성공률(압축 없음)      # 기준 성공률 5% 미만 태스크는 제외
```

24 태스크 × 50 에피에서 K2 평균 유지율 0.916, K3 0.754. **압축에 강한 데이터셋이다** --
게이트는 기본적으로 관대해야 하고, 막을 곳만 막는 것이 맞다.

### 검증된 성질

- 기준 성공률과 유지율은 무관하다(K2 +0.024, p=0.913). 즉 "원래 어려운 태스크가 압축에
  약하다" 는 교란은 없다.
- 유지율의 태스크 순서는 K2/K3 에서 재현된다.

## 4. 국면 정의 (계산만으로, 문항의 답을 미리 알려주지 않는 값만 사용)

`judge_ab.phase_of` + 그리퍼 방향으로 6단.

```
grip_change 있음 → 닫힘만: 파지 · 열림만: 해제 · 둘다: 전이(둘다)
아니면  아래로 & 감속 → (쥐고 있으면) 놓기 (아니면) 접근
        쥐고 있고 안 내려감 → 운반
        그 외 → 쥐지 않았으면 접근, 쥐었으면 운반
```

**주의: "운반" 은 자유 이동이 아니다.** 문 손잡이를 쥐고 당기는 구간도 여기 들어간다.
태스크 종류(물체운반 대 기구조작)로 한 번 더 갈라 봐야 한다.

실제 프레임 비율(719 장면 표본): 접근 61% · 운반 31% · 파지 3% · 해제 4%.

## 5. 판정기 (VLM) 와 응답 형식

```
scripts/vlm_gate_cosmos.py --serve --port <p>     모델 무관 (id 에 cosmos 면 Cosmos, 아니면 AutoModelForImageTextToText)
환경:  cosmos_judge_venv (py3.13, transformers 5.12.1)
```

**반드시 `mode="text"` 로 쓴다.** 모델이 답을 쓰게 하고 서버가 파싱한다. `n_grade` 만
주고 `mode` 를 빼면 강제된 슬롯의 로짓을 argmax 로 읽는 옛 경로로 떨어진다 -- 모델이
답한 것이 아니라 argmax 가 답한 것이 된다.

**등급 분포(`grade_probs`)가 반드시 실려야 한다.** 없으면 정수 등급으로 떨어지고
conf 가 계단이 된다(tau=0.50/0.517/0.55 가 같은 설정이 된다). 확인:

```
라벨 jsonl 에 "gp" 가 값으로 들어 있는 행의 비율이 100% 인가
```

0% 면 `ratio_label.py` 가 `SystemExit` 으로 죽는다(`ALLOW_INT_GRADES=1` 로만 우회).
포트는 고정하지 말고 빈 포트를 찾는다 -- 같은 노드에 두 판정기가 앉으면 `Errno 98`.

## 6. 기존 라벨 (비교 기준)

```
output/_gate_distill/robocasa_contact_ratio_instr.parquet    2,044,657행
  episode_index int32 · frame_index int32 · A..E int8 · fixed int8
  ratio float32 · task object · instruction object · conf float32
```

`fixed` 는 접촉 경계 플래그다(외부 접촉 데이터셋 병합, 액션에서 재계산 불가).
새 라벨의 `fixed` 는 여기서 (ep, f) 로 가져온다.

**이 파일의 conf 는 정수 등급으로 만들어졌다** -- 2026-09-12 이전 라벨은 전부 그렇다.

## 7. 계산 리소스

실측 처리량 **12,000 행 / GPU-시간** (phase9 계열 46잡 170 GPU-시간에 고유 204만 행,
선점 손실·재시도 포함).

| 규모 | 프레임 | GPU-시간 |
|---|---|---|
| 실험 한 바퀴 (762 장면) | 762 | 0.4 |
| stride 8 전량 | 256k | 21 |
| stride 4 전량 | 511k | 43 |

파티션은 같은 노드를 여러 이름으로 노출한다. **과금이 다르다.**

| 파티션 | PriorityTier | GPU 과금 |
|---|---|---|
| `*_urgent` | 4 | ×1 |
| `*_premium` | 3 | **×3** |
| 기본 | 2 | ×1 |
| `background` | 1 | **×0.2** |

대량 작업은 `background` + `--time=3:00:00` + 1-GPU 배열 + `--requeue`. 스케줄러가
`sched/backfill` 이고 대기 잡의 다수가 2일을 요청하므로 짧은 잡이 빈틈에 들어간다.
선점되지만 worklist 로 재개하므로 진행 중 청크만 잃는다.

fairshare 는 순위 기반이라 사실상 순서를 정하지 않는다 -- 실제 우선순위 분해에서
FAIRSHARE 7~267 대 PARTITION 1000~2000 이다.
