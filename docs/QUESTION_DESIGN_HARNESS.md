# 압축 게이트 문항을 깎는 절차

전제는 `EVAL_RESULT_PRECONDITIONS.md` 에 있다. 그것이 갖춰져 있다는 가정에서, 이 문서
하나로 문항 설계를 처음부터 재현할 수 있게 쓴다. 사람이 읽고 따라 해도 되고, 에이전트
에게 이 문서를 주고 시켜도 된다.

---

## 0. 무엇을 만드는가

한 순간(1초, 16스텝)의 로봇 동작을 보고 **그 구간을 절반 속도로 실행해도 되는지**를
0~1 로 내는 `conf`. VLM 에게 다섯 문항을 1~5 등급으로 묻고 가중합한다.

```
conf = (1 + Σ_가점 w·g − Σ_감점 w·g) / 2,     g = (등급 − 1) / 4
게이트:  압축 여부 = conf ≥ τ
```

문항 정의는 `scripts/phase9_checks_v*.py` 한 파일에 모여 있다 -- `SIGN`(부호),
`WEIGHT`(가중), `SCALE`(등급표), `_AXES`(문항 다섯), `GUIDANCE`(시스템 문구), `NGRADE`.

---

## 1. 규칙 (어기면 결론이 뒤집힌다)

**R1. 문항은 태스크당 지표로 채점하지 않는다.**
목표(폐루프 유지율)는 태스크당 숫자 24개다. 거기에 맞춰 문항·가중을 밀면 라벨이 태스크
상수로 수렴한다 -- 실제로 상관을 +0.311→+0.552 로 올리는 동안 태스크몫이 0.737→0.984
가 됐다. 그 지점의 라벨은 24행 룩업표와 같고, 그 표는 이미 있다.
**주 채점은 국면 지표로 하고 태스크 상관은 부호 확인용으로만 쓴다.**

**R2. 한 번에 한 가지만 바꾼다.**
문항 셋을 함께 바꿨더니 둘은 살아나고 하나는 방향이 깨졌는데, 어느 것 때문인지 가르려고
한 바퀴를 더 써야 했다. 문항끼리 간섭한다 -- B 문구만 바꿔도 D 의 해제 등급이
3.51→2.96 으로 움직인다.

**R3. 국면 표본을 균등하게 맞춰 놓고 시작한다.**
무작위로 뽑으면 파지가 7% 뿐이라 그 23개 장면에 과적합한다.

**R4. 등급 분포를 반드시 저장한다.** 없으면 conf 가 계단이 되어 역치가 안 먹는다.

**R5. 가중은 라벨링 뒤에 정한다.** 등급과 기댓값 등급을 저장하면 가중은 몇 번이든 다시
계산된다. 라벨링 전에 얼려야 하는 것은 **문구와 계산 사실**뿐이다.

**R6. 문항을 고치기 전에 그림을 본다.** 손목 화면으로 좁은 곳을 판별하는 문항을 만들었다가
그림을 보고 버렸다 -- 손목 화면은 언제나 대상이 꽉 차 있다.

**R7. 등급 분포로 "죽은 문항" 을 먼저 찾는다.** 부호나 가중을 의심하기 전에, 그 문항이
화면에서 인식되는지부터 본다. D 는 719/719 전부 1등급이었다 -- 가중 0.15 를 쥐고
conf 에 아무것도 기여하지 않았다.

## 2. 채점표

한 판을 만들면 아래를 전부 낸다. `scripts/phase_scorecard.py` 가 한다.

| 지표 | 뜻 | 방향 |
|---|---|---|
| **국면몫** | 태스크 효과를 지운 잔차 중 국면이 설명하는 몫 | 높을수록 |
| **남는몫** | 태스크·국면으로 설명 안 되는 몫 | 낮을수록 |
| **파지−접근** | 가장 위험한 국면과 가장 안전한 국면의 conf 차 | 음수로 클수록 |
| 태스크몫 | 태스크 평균이 설명하는 몫 | 참고 (낮다고 좋은 게 아니다) |
| K2 / K3 상관 | 태스크 평균 conf 대 폐루프 유지율 순위상관 | **양수여야** (부호 확인) |
| 문항별 국면 최고 | 각 문항이 의도한 국면에서 최고인가 | 의도와 일치 |
| 문항별 4등급 이상 비율 | 그 문항이 발동은 하는가 | 0% 면 죽은 문항 |

**태스크몫이 낮은 것 자체는 좋은 신호가 아니다.** 무작위 라벨은 태스크몫이 0 이다.
낮은 태스크몫이 의미를 가지려면 그 자리를 국면몫이 채워야 한다 -- 자체집계 판이 태스크몫
0.664 로 가장 낮았지만 국면몫도 0.170 으로 가장 낮고 남는몫이 0.278 로 가장 높았다.

## 3. 절차

### 3-1. 장면 집합

```bash
python scripts/build_phase_balanced_scenes.py 10
# -> _tmp/selfagg_bias/scenes_phase.json
#    762 장면 · 접근 240 · 파지 180 · 해제 162 · 운반 180 · 에피 160
```

한 에피소드가 한 국면을 2개까지만 차지하게 막는다. 안 그러면 태스크 안 변동이 아니라
그 에피의 특성을 재게 된다.

### 3-2. 기준선 라벨링

```bash
CHECKS=phase9_checks_v3 GP_N=800 \
  python scripts/gp_conf_check.py <port> _tmp/selfagg_bias/scenes_phase.json _tmp/.../ph_base.jsonl
```

762 장면에 GPU 1대로 약 25분. 이어서 돌 수 있다(같은 파일에 append, (ep,f) 건너뜀).

### 3-3. 진단 -- 무엇이 고장났는지

```bash
python scripts/phase_scorecard.py _tmp/.../ph_base.jsonl
```

보는 순서:

1. **4등급 이상 비율이 0% 인 문항** → 죽은 문항. 문구가 이 데이터셋 화면과 안 맞는다.
   부호·가중을 건드리기 전에 문구를 고친다.
2. **국면 최고가 의도와 다른 문항** → 겨눈 곳이 틀렸다.
3. **4등급 이상이 60% 넘는 문항** → 포화. 거의 항상 "그렇다" 라 가르지 못한다.
4. **국면 간 표준편차** → 그 문항이 실제로 가르는 폭. 가중과 견줘 본다.

발동해야 할 장면 비율과 같이 봐야 한다. 해제가 21% 인데 D 가 90% 1등급인 것은 정상이다
-- 대상 안에서 45%, 대상 밖에서 0.0% 면 잘 가르는 것이다.

### 3-4. 그림 확인 (R6)

```python
# 국면별 · 태스크별로 타일을 이어붙여 직접 본다
# _tmp/look/{접근,파지,해제,운반}.png · tight.png (기기 안으로 들어가는 태스크)
```

문항이 묻는 것이 화면에 실제로 보이는지 확인한다. "옆 화면에서 팔이 문틀에 가려진다" 는
사람 눈에는 명확했지만 모델은 그렇게 쓰지 않았다 -- 그림 확인은 가설을 만드는 단계이지
결론이 아니다.

### 3-5. 한 가지만 바꿔 다시 (R2)

`phase9_checks_vN.py` 를 만들고 `CHECKS=phase9_checks_vN` 으로 3-2 를 반복한다.
부호·가중·등급표·GUIDANCE 를 안 건드렸는지 확인:

```python
assert A.WEIGHT==B.WEIGHT and A.SIGN==B.SIGN and A.GUIDANCE==B.GUIDANCE and A.SCALE==B.SCALE
```

### 3-6. 가중 (라벨 위에서, GPU 없이)

```bash
python scripts/fit_phase_weights.py _tmp/.../ph_vN.jsonl
```

에피소드를 반으로 갈라 한쪽에서 정하고 다른 쪽에서 채점한다. 국면 판별력(국면 간 표준
편차)에 비례하는 규칙을 제공하지만 **그대로 쓰지 말 것** -- 발동률 10% 짜리 문항에
가점의 절반을 주는 배분이 나온다. 등급 1 은 g=0 이라 가중을 올려도 기여가 0 이므로,
드물게 발동하는 문항에 큰 가중을 주면 그 10% 에서만 요동친다.

### 3-7. 집계 방식

문항별 등급을 받아 우리가 가중합하는 판(산수)과, 부호·가중을 알려 주고 최종 등급 하나를
받는 판(자체집계)을 비교했다. **산수가 낫다.**

| | 국면몫 | 남는몫 | K3 | 작동점 |
|---|---|---|---|---|
| 산수 | 0.708 | 0.101 | +0.502 | τ 로 조절 |
| 자체집계 | 0.535 | 0.261 | +0.467 | Z≥4 가 16% 로 고정 |

자체집계는 프레임별 신호가 적고 잡음이 2.6배이며, 5단계가 곧 답이라 되돌릴 손잡이가
없다. **그리고 문항별 진단이 안 된다** -- 죽은 D 를 찾은 것이 문항별 등급을 따로 받았기
때문이다.

### 3-8. 역치

라벨을 만든 뒤 국면별 압축 허용률로 정한다. 실제 국면 비율로 가중해서 본다(장면 집합은
국면균등이라 파지가 과대표집돼 있다).

```
τ=0.35  전체 55%  접근 64%  파지 13%  해제 36%  운반 45%
τ=0.25  전체 84%  접근 90%  파지 42%  해제 81%  운반 80%
τ=0.22  전체 91%  접근 96%  파지 43%  해제 93%  운반 88%
```

접근−파지 격차가 τ 전 구간에서 48~57%p 로 안정적이다. robocasa 는 압축에 강하므로
(K2 평균 유지율 0.916) 관대한 쪽에서 고르고 파지만 막는다.

## 4. 계산 사실 (문항만큼 중요하다)

문항과 함께 다섯 문장이 사실로 주어진다(`robocasa_descriptors.facts_text`). 정지 화면
으로 볼 수 없는 것은 여기서만 들어온다.

**국면 판별 전체가 이 중 첫 줄에서 나온다.** 정지 화면 한 장으로는 그리퍼 개폐를 볼 수
없으므로 그 줄이 유일한 경로다.

검증된 것:

| 사실에 넣은 정보 | 결과 |
|---|---|
| **그리퍼 방향** (파지인가 해제인가) | **통했다.** 닫힘-열림 conf 차 -0.003(p=0.86) → **-0.121(p=0.0009)** |
| **속도 분위** (절대 경계 → 전체 분포 백분위) | **통했다.** 절대 경계 0.12/0.50 은 하위 1.6%/46.6% 를 잘라 세 갈래 중 하나가 죽어 있었다 |
| 그리퍼 시점 (16스텝 중 몇 번째) | 무익 (p>0.3). 문장만 길어진다 |
| 창 밖 지평 (다음 파지까지 N스텝) | 무익 (p=0.82), 잡음 증가 |

**규칙이 보인다: 모델은 범주형 사실은 쓰고 숫자는 안 쓴다.** 새 정보를 넣을 때는 숫자가
아니라 범주로 준다. 그리고 줄 수는 다섯으로 고정한다.

| | K3 상관 | 국면몫 | D 발동 | E 발동 |

부호가 뒤집힌 자리는 문항 A 한 줄이었다 -- "버튼·스위치·다이얼은 접촉 한 번이 어긋나면
실패한다" 가 감점 가중 2/3 을 쥐었는데, 폐루프에서 그 태스크들이 가장 강했다
(`CoffeePressButton` 유지율 1.22 -- 압축이 성공률을 올렸다).

국면별 conf 는 물리적으로 단조롭다:
`파지 0.222 < 해제 0.344 ≈ 운반 0.346 < 접근 0.403`.

**남은 것**: B 가 포화(53% 가 4등급 이상)이고, A 가 3등급에 63% 몰려 있다. 둘 다
방향은 맞다.
